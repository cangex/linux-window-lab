# P1：AP 启动基础验证

状态：**P1 已完成并通过验收**（2026-10-13）。

## 已实现的机制

在独立的 `lwlab-boot` 中运行定制 Linux `6.18.0-rc3-lwlab-p1`，早期预留 guest physical `0x180000000–0x180ffffff` 的 16 MiB RAM。CPU 4–7 从 Linux 下线，CPU 4 经已有 ZDU AP trampoline 转入独立的平坦 x86-64 payload，CPU 0–3 继续运行主 Linux。

payload 设置自己的栈、CR3、GDT 和 IDT，通过版本化交接结构和 mailbox 回写 generation、实际 APIC ID、阶段、心跳、TSC 和错误码。主 Linux 完整校验握手之后才标记 ready；超时或异常不会归还 CPU/内存。启动等待期间保持 kexec 串行化，完成后清理临时 warm-reset 向量。

实现、ABI 和复现命令见 [P1 说明](../p1/README.md)。确切源码、配置与二进制哈希见 [源码清单](../p1/sources.lock.json)、[实测构建清单](../p1/tested-build.json)。

| 外层平台 | QEMU 8.2.2 / KVM / OVMF 2024.02，Q35 8.2 |
| 目标 VM | `lwlab-boot`；8 vCPU、16 GiB RAM |

## 验收方法

每一轮从 VM `shut off` 状态启动，并验证不同的 Linux boot ID 和 payload generation。Linux 在 AP 启动前 5 秒与宿主机建立 TCP 连接，整个测试不重新连接；每秒执行文件写入、fsync、回读校验和 mailbox 采样。宿主机记录原始流并周期性 ping。

正常场景要求每个启动后的采样均满足目标身份、私有上下文、magic 和 generation 检查，且心跳严格递增。故障场景分别让 payload 停驻在 entered 阶段，以及执行 UD2；检查返回错误和失败状态，并继续运行 Linux 网络与文件 I/O。

每轮验证 12 类拒绝行为：在线 CPU、错误版本、CPU 0、零 generation、畸形命令、越界内存、错误大小、非法入口、范围外入口、重复启动、启动后重载、启动后重新 online。离线复核脚本检查完整原始样本、时间跨度、全部返回码和内核日志。

## 最终验收结果

最终矩阵与独立复核均通过。10 次正常场景和 2 次故障注入合计 12 个不同 boot ID、12 个不同 generation；每轮 12 类拒绝检查均通过。

- 正常冷启动：**10/10**，APIC ID、generation、magic、私有 CR3 和栈均匹配，后续心跳逐样本递增。
- 长稳：guest 按 **1800 秒**截止条件完成运行，共收到 **1802 个样本**（包含启动前样本），最终心跳 **480673**。宿主从首个启动后样本收到最终结果的跨度为 **1799.925 秒**，与 guest 时间窗口的差别来自采样边界；离线复核允许 2 秒边界偏差。
- 正常场景最大 TCP 样本间隙：**1.659721 秒**。所有运行均保持同一条 TCP 连接，ping 失败数为 0，文件 fsync/回读校验通过。
- 故障注入：entered 后停驻返回 Linux `ETIMEDOUT=110`；UD2 返回 `EIO=5`，mailbox 为 `stage=255 / payload_error=3`。超时测试最大采样间隙 **4.649416 秒**，包含控制调用预期的约 3 秒等待；其余运行通过相同阈值检查。
- 每轮启动清理日志均存在；完整 dmesg 未出现 `WARNING:`、`BUG:`、`Oops:` 或 kernel panic。最终环境快照的内核 taint 为 0。

## 开发中发现并修复的问题

1. 安装脚本初版将 modules archive 的 `lib/` 目录直接解包到根目录，替换了 Ubuntu 的 `/lib` 符号链接，导致 initramfs 生成失败。已恢复链接，并改为临时目录解包后仅复制 modules 内容；最终安装通过。
2. 原 P0 的单插槽、双 NUMA 虚拟拓扑在定制内核中触发跨 NUMA 的 LLC 警告。`lwlab-boot` 改成两个插槽分别对应两个节点；新启动的内核 taint 为 0。
3. 复用 AP 路径成功发送启动请求后没有调用传统 warm-reset 向量清理。P1 在握手成功、异常或超时后补上匹配的清理，IPI 发送失败仍由原路径清理。
4. Python 缓冲写入在 sysfs 命令超时后重复 flush，导致原始 `ETIMEDOUT` 被重复启动的 `EBUSY` 覆盖。测试工具改用单次 `os.write()`，不重试控制事务；同时修正 runner，先收集 guest 退出日志再报告 observer 错误。

这些初期运行保留在服务器，未计入最终验收。

## 能力边界

- 证明的是本配置下一个 AP 运行独立 payload、主 Linux 同时运行，尚未启动分区 UEFI、WinPE 或 Windows。
- P1 复用早期内存池和 AP trampoline，以 firmware loader 装载平坦 payload；未接入完整 KHO/ZDU 更新事务或 kexec-tools。
- 心跳依靠 PAUSE/RDTSC，没有 AP 本地定时器、中断业务、PCI 设备或固件 Runtime Services。
- 只支持整台实验 VM 关闭后重启恢复；没有 AP 独立重启、资源回收或动态调整。
- 1 GiB 恒等映射不是访问隔离。两个系统间访问保密不是本项目的目标。
- 测试 I/O 负载用于检测运行连续性；TCP 间隙不代表实时性保证。本配置没有宿主 CPU 独占或 NUMA 绑定，不作性能收益结论。
