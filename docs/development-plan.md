# Linux–Windows multikernel 开发计划

更新：2026-10-14。状态：P0–P5 已完成；P6 多核、长稳和生命周期进行中（见 [进度](2026-10-14-p6-progress.md)）；P7 裸机迁移；P8 观察系统完善与最终评估。P5 完整 Windows、独占 NVMe 与语义解析结果见 [P5 报告](2026-10-14-p5.md)。P4 两次冷启动分别通过约 5500 万次外部读取尝试，见 [P4 报告](2026-10-14-p4.md)。P3 在同一 VM 内通过 10 次 WinPE 冷启动与 31 分 30 秒共存检查，见 [P3 报告](2026-10-14-p3.md)。P2 的 10 次冷启动、九项 EFI 自检及平台协调结果见 [P2 验收报告](2026-10-13-p2.md)。P1 的 10 次冷启动、30 分钟连续性及故障注入结果见 [验收报告](2026-10-13-p1.md)。

## 目标与当前起点

目标是在同一物理机器的不同资源分区中运行 Linux 与 Windows，由 Linux 组织启动，并从 Windows 常规访问控制接口之外读取和理解其数据。优先探索无常驻虚拟化层的方案；是否能满足这一目标，必须通过共享平台状态和 Windows 初始化实验判断。

P0 已完成：`lwlab-dev` 为 8 vCPU / 16 GiB 的 QEMU/KVM + OVMF Ubuntu 开发 VM，工具链、UEFI 启动、I/O 和冷启动检查通过，具有冷备份。`lwlab-dev` 保留普通 Ubuntu 内核。P1 已在独立 `lwlab-boot` 部署定制内核、静态预留 RAM 与 AP payload；P3 已获得并固定官方 WinPE 介质，完成单 AP 启动和 Linux 持续运行验证。

第一项可展示成果定义为：**Linux 的用户态和 I/O 持续运行，指定 AP 执行独立 payload，Linux 能读到目标 CPU 回写的启动阶段和心跳。**

## 实验组织与范围

- `lwlab-dev` 保留为构建环境。P1 开始时，从冷备份派生独立的 `lwlab-boot` 目标 VM，使用独立可写磁盘、NVRAM、MAC/IP 和日志，避免启动失败同时损坏构建环境。`lwlab-boot` 已在 P1 中创建并完成验证。
- WinPE 镜像就绪后，另外创建可回滚的标准 WinPE 基线 VM，先排除镜像自身问题。正式共存实验始终发生在一台 `lwlab-boot` 内。
- 外层 KVM/QEMU 提供可恢复的实验机器。项目内部不再套一层 Windows VM，才属于本阶段的 multikernel 路线验证；它仍不能直接证明裸机兼容性或性能收益。
- 启动资源先静态划分。候选为 Linux 使用 vCPU 0–3，目标分区使用 4–7；先只启动其中一个目标 CPU，其余保持停驻。必须实测 Linux CPU 编号、APIC ID 和 NUMA 关系。
- 内存按实际 guest UEFI/e820 布局选取，先在开机时预留，暂不做运行中任意内存迁移。不能把 16 GiB 简单当成连续物理区间，也不沿用本地 TCG 配置中的地址。
- 原型初期采用明确记录的 Secure Boot/VBS/Hyper-V 配置；以不修改 Windows 系统二进制为首选。测试程序或用于建立真值的驱动可以合作，须与最终外部定位能力区分。
- 动态扩缩容、休眠、跨系统共享文件系统写入和访问保密隔离不进入首个原型。

## P1：固定源码并建立可靠 AP 启动

### P1a：源码与构建基线

1. 找回并核对既有 KHO/multikernel 原型的完整源码、kexec-tools、配置和补丁。历史记录中的 `5a713e2...`（原型）和 `d75950c...`（后续连续性验证）只是候选证据，不能未经核对视为当前可用的构建基线。
2. 优先复用 AP 启动、CPU 下线、预留内存和连续性测试机制。NUKA 的应用机制及 ZDU 的事务语义不自动纳入项目。
3. 冻结主内核、工具链、kexec-tools、EDK2 的确切提交和配置，记录源码来源及必要许可证。新仓库保存补丁与获取/构建脚本，不提交整个历史工作区。
4. 在 `lwlab-boot` 安装主内核；保留普通 Ubuntu 的救援启动入口与外部恢复能力。验证主内核本身的网络、磁盘和 UEFI 状态。

### P1b：独立 payload 与启动握手

审计入口包括 `kernel/kexec_core.c`、`kernel/kexec_file.c`、`kernel/kexec_handover.c`、`kernel/multikernel/`、`arch/x86/kernel/smpboot.c` 和 `trampoline_64_bsp.S`，最终路径以冻结源码为准。

本地代码审阅已经发现两个必须处理的点：AP 唤醒函数返回成功后就标记 active；KHO finalization 失败仍会继续尝试启动。计划将“启动请求已发送”和“目标实际运行”分开，并让必需启动信息校验失败时停止启动。

定义独立于 Linux `boot_params` 的版本化交接格式，至少包含 magic、版本、长度、启动 generation、目标 APIC ID、入口地址、内存范围、栈/页表、日志区和 mailbox。明确地址均为哪一级物理地址、对齐、映射和调用约定。Windows 阶段再加入平台描述指针。

状态至少区分：`prepared → loaded → start-issued → payload-entered → payload-ready`，另有 `failed`。mailbox 由目标 CPU 写入 generation、实际 APIC ID、阶段、递增心跳和错误码；Linux 使用明确定义的内存屏障读取。不能仅靠旧日志、旧 magic 或 IPI 发送成功判定启动。

测试 payload 从最小循环开始，先不触碰 PCI、全局时钟、固件服务或整机复位。设置自己的必要 CPU 上下文，逐步验证长模式、栈、异常日志，再增加目标 CPU 的本地定时器。检查启动 CPU 作为硬件 AP 的身份是否被后续代码假设为 BSP，不能通过修改 ACPI 就假设解决。

第一版不实现启动后资源自动回收。启动超时后保持相关 CPU/内存保留，靠重启实验 VM 恢复，避免仍在执行的 CPU 使用已被回收的内存。

验收：10 次独立冷启动均有正确的目标握手；至少一次连续 30 分钟心跳与 Linux 网络/文件 I/O 检查；非法入口、未下线 CPU、越界内存和错误交接版本均被拒绝。结果包含 Linux boot ID、payload generation、内核与镜像哈希。

## P2：独立的分区 UEFI

已完成：固定分区 EDK2 DXE、HOB/ACPI、只读内存盘、AP 本地定时器及所测 runtime 服务通过 10 次冷启动。Linux 需禁用 shorthand IPI 广播并独占 COM1；详见 [实现和限制](../p2/README.md)。

采用 EDK2 `UefiPayloadPkg` 作为候选起点，而不是把整机 `OVMF_CODE.fd` 直接当作 kexec 镜像。先固定 EDK2 提交，再适配入口/HOB 或对应版本支持的交接结构，只描述本分区。

当前上游配置具有内存盘、存储、复位、定时器等可选路径，因此“编译通过”不能说明其默认配置适合共存。当前实验 VM 关闭 HPET，而被查看的 payload 配置默认选择 HPET；应首先审计并验证 LAPIC/可用时钟路线及其 CPU 局部影响。[EDK2 UefiPayloadPkg 配置](https://github.com/tianocore/edk2/blob/master/UefiPayloadPkg/UefiPayloadPkg.dsc)

| 子项 | 必须完成的设计与验证 |
| --- | --- |
| 内存 | 分开空闲内存、payload、ACPI、页表、栈、mailbox 和 runtime 页；跨内核读映射使用一致缓存属性 |
| ACPI | 生成独立 RSDP/XSDT，按实际需求处理 MADT、FADT/DSDT、NUMA 表、PCI 描述和调试设备；地址、处理器 ID 与硬件一致 |
| CPU | 分区启动 CPU、其余 AP 停驻与后续唤醒；禁止广播操作误伤 Linux CPU |
| 中断/时钟 | LAPIC、IOAPIC、MSI、全局定时器与中断重映射逐项确定归属和允许的操作 |
| 存储/控制台 | 优先评估预加载启动介质和分区 RAM disk；保留独占控制器备选；双串口明确归属 |
| Runtime Services | 明确变量、时间、虚拟地址转换和复位策略，不能把两个 OS 都直接接到整机固件入口 |

`ExitBootServices()` 与 `SetVirtualAddressMap()` 是不同的操作，分别验证。分区的虚拟地址转换不能改变主 Linux 使用的固件上下文；不能共享一套运行时服务后仅靠 Linux 内部锁声称完成串行化。UEFI 对跨 CPU 的 runtime 调用有重入约束。[UEFI Runtime Services](https://uefi.org/specs/UEFI/2.10/08_Services_Runtime_Services.html)

以专用 EFI 自检程序检查 `AllocatePages`、`GetMemoryMap`、协议查找、镜像加载、文件读取、事件与退出服务等实际需求，再验证 runtime 路径。允许对明确不支持的服务按规范返回错误，但必须记录 Windows 实际是否接受；不能用任意成功返回值掩盖缺失实现。

验收：EFI 自检运行于被分配的 CPU；分配结果均在允许范围；通过服务退出测试后 Linux 的心跳和 I/O 仍正常；至少 10 次冷启动复现。该阶段的结果仅证明已测试服务，不等同于完整 UEFI 兼容认证。

## P3：Windows 11 x64 WinPE 并行启动

已完成单 AP 验收，实测与限制见 [P3 报告](2026-10-14-p3.md)。P3 扩展为 1536 MiB 主 RAM + 两段低端 RAM，给 Windows 独占 IOAPIC/HPET，Linux 使用 `noapic hpet=disable`；P2 的 256 MiB/无 HPET 配置保留为历史阶段。多核 Windows 尚未测试。

按 [WinPE 制作说明](winpe.md) 准备官方 ADK/add-on 镜像，先在普通 OVMF 基线 VM 到达用户态并冻结哈希，然后接入分区启动链。

按观测证据分别记录：启动管理器执行、加载器阶段、`ExitBootServices`、内核早期、WinPE 用户态。无法从外部日志确定的阶段标注为未确认；图形标志或 AP 心跳不作为 WinPE 启动完成证据。

先用单目标 CPU，之后扩展到完整分区 CPU 集合。从 RAM disk 引导可减少早期设备接管，但仍需验证 Boot Manager/BCD、WIM、启动文件和驱动依赖，不能假设存在 EFI 文件系统就一定可启动。

把故障分为服务缺失、平台描述矛盾、CPU/AP 启动、设备驱动、共享状态破坏五类。只对有证据的路径增加日志或定点调试；QEMU 调试信息不代表覆盖了所有 KVM 内部执行、MMIO 或端口访问。

验收：WinPE 启动到命令行并运行测试程序，Linux 同时通过 30 分钟连续性检查；至少 10 次冷启动。另行记录多核启动是否通过，不用单核成功替代多核结果。

## P4：已知数据的外部读取

已完成：两次独立冷启动、只读后端、已知发布协议与三类故障注入，见 [P4 报告](2026-10-14-p4.md)。

Windows/WinPE 测试程序产生带启动随机标识、序号、长度和校验值的数据。可先用合作分配/报告缓冲区位置的测试驱动建立真值，或验证过的标记定位方式；位置报告不应承担实际数据传输。此阶段明确属于合作定位的读取验证。

Linux 侧实现限定实验分区范围的只读后端，避免依赖 `/dev/mem` 恰好可用。处理映射类型、缓存属性、页边界及失效 generation；读到的目标页不能被 Linux 分配器同时分配。

写端按约定的序号发布协议更新；读端重复读取序号和内容，拒绝正在写入或跨版本的数据。校验值用于发现内容错误，不能单独证明任意 Windows 对象的原子快照。

验收：不少于 100 万次读取尝试，已接受样本均与协议真值一致，并公布接受率、重试率、检测到的不一致、吞吐、CPU 开销和延迟分布。故障注入至少覆盖写入中途、旧 generation 和缓冲区撤销；本阶段不证明自动发现任意对象。

## P5：完整 Windows 与语义解析

已完成固定 build、单 Windows CPU 的短时验证：两次冷启动、真值对照、辅助页撤销后的独立发现、进程/DLL 生命周期和旧 generation 拒绝。见 [P5 报告](2026-10-14-p5.md)。整台 VM 冷启动不代表 Windows 分区独立重启能力。

先接入具有受控复位范围的独占存储设备或控制器，再启动固定 build 的完整 Windows。设备枚举、配置空间、中断和 DMA 必须使用一致归属；仅划分磁盘分区不能等价为划分控制器。若仍需要代理设备或最小虚拟化，应单列为方案变化。

语义解析按页表/地址翻译、内核与模块、进程和选定测试对象的顺序推进。记录 Windows build、PDB GUID/age 与结构来源，不将偏移硬编码为通用版本。处理大页、非驻留/失效页面和采样期间页表变化。

先用 Windows 内部测试工具提供真值做交叉验证，之后另设验收：关闭定位辅助通道，Linux 能否独立发现并读取选定对象。两项能力分别报告。运行中目标对象的重复读取只能提供有限一致性，需要跨对象快照时另行设计暂停协议，并说明对 Windows 的扰动。

验收：完整 Windows 应用与 Linux 同时运行；冻结版本上选定对象与真值相符；进程退出、模块变化和重启 generation 变化时不把旧数据当成当前数据。文件缓存、磁盘文件系统解析和多版本覆盖在首组对象通过后再加入。

### P6：VM 内多核、长稳和生命周期

保留当前 QEMU 平台，先解决可持续使用的 Windows 镜像和宿主机资源预算，
再增加 2/4 Windows CPU。沿用 Linux 0–3、Windows 4–7 的拓扑起点，
重新验证 AP 启动、Windows IPI、时钟和中断归属。

必做验收为 1/2/4 CPU 回归、10 次固定配置冷启动、2 小时和 24 小时联合负载，
以及辅助页撤销后选定对象的持续观察。改善 P5 的时间对齐与真值覆盖，报告
不可用、排除、错误和延迟，不能仅对少量幸存样本计算正确率。

Windows 崩溃、关机、重启及设备故障分开测试。分区重启要求 Linux boot ID
不变、全部 Windows CPU 停驻、设备 DMA/中断停止、generation 失效后再装载。
未能证明资源静止时保持预留，不能清空或返还给 Linux 分配器。EFI ResetSystem
适配不视为所有复位路径已经受控。

P6 的稳定共存验收与独立恢复验收分别记录；恢复失败时保留“稳定共存通过、
恢复未完成”的状态，随后明确继续直接路线或另建最小虚拟化备选，不能将整台
VM 重启算作分区恢复。P7 单核迁移可在稳定共存通过后推进，继承恢复限制。

### P7：裸机迁移

需要专用测试机器或明确的整机测试窗口、独立恢复入口及可独占的设备。
当前服务器上运行其他业务，现有 VM 实验范围不自动扩展为宿主机裸机改造。

先完成真实 CPU/APIC/NUMA、RAM、PCI/复位域、固件和中断资源清单，消除
P5 固定 QEMU 地址依赖。按 AP payload → 分区 UEFI → WinPE → 完整 Windows
顺序推进，单核成功后逐步扩展多核，再验收外部观察和持续负载。

目标是固定一台机器上的 10 次冷启动、2 小时及 24 小时联合负载，以及 P6
已有生命周期能力的实机复验。保留救援启动项，记录硬件/固件版本与失败边界。
无需为跨系统保密强制加入隔离；IOMMU/中断重映射是否启用取决于实测协调需求。

### P8：观察系统完善与最终评估

将已通过的页表、进程、内核模块、用户模块和指定进程虚拟地址读取整理为
版本化只读接口。结果携带 generation、对象身份、采样起止时间、profile 身份
和一致性/不可用原因。支持至少两个固定 Windows build，并在未知版本上拒绝
解释；更换镜像后重做对应启动与观察回归。

比较 Windows 裸机独占、优化 KVM（专用 CPU/NUMA/设备直通）及本项目裸机
共存；分别测观察关闭、开启及不同频率。匹配资源、版本和工作负载，报告
吞吐、尾延迟、CPU/内存、启动/恢复时间、正确率、覆盖率与发现延迟。
不把 QEMU 内的功能实验数据直接用于裸机性能结论，也不把原始页吞吐等同于
新数据速率或语义处理吞吐。

最终交付可复现构建/运行/验证命令、原始数据索引、分析脚本、平台支持矩阵与
明确的能力限制。研究结论由数据决定；不预设新架构必然比 KVM 更快。

## 路线取舍条件

| 观察到的情况 | 处理方式 |
| --- | --- |
| payload 接口缺失或描述错误 | 留在直接共存路线，修复接口与配置后重测 |
| 已知共享寄存器操作可通过平台适配或协作约束 | 记录约束并验证，不自动增加虚拟化层 |
| Windows 必须操作 Linux 同时依赖的共享状态，现有适配无法协调 | 保存最小复现和 Linux 受影响证据，评估静态分区加最小虚拟化层 |
| 仅故障恢复依赖整机复位 | 将可用生命周期能力降为受限原型，单独决定是否引入监控层 |
| 同一问题连续两轮实验无新证据 | 停止盲目修改，补观测或做对照；时间消耗本身不证明路线不可行 |

使用最小虚拟化层时必须写清拦截对象和常驻职责，并单独命名/记录该路线。跨系统读取仍是目标，不因为引入硬件机制就改成安全隔离项目。

## 代码组织与结果记录

拟增加 `sources.lock.json`、`patches/linux/`、`patches/kexec-tools/`、`firmware/LwPartitionPkg/`、`payloads/ap-probe/`、`observer/`、`windows/marker/`、`tests/` 与 `configs/`。P1 的当前交付集中在 `p1/`：源码锁定、覆盖层、完整配置、构建安装脚本、payload 和验收工具；P2 交付集中在 `p2/`：固件组件、资源生成器、内核覆盖层、源码锁定、构建安装与验收工具；P3 交付集中在 `p3/`：官方介质构建、引导适配、低端 RAM/IOAPIC/HPET/GOP、用户态遥测及双系统验收；P4/P5 交付分别集中在 `p4/`、`p5/`，包含只读后端、Windows 测试程序、独占 NVMe、版本化解析器和验收工具。

单一版本化资源清单作为 loader、UEFI 生成和验收工具的共同输入，包含 CPU/APIC 映射、带类型的物理内存区间、设备和寄存器归属、串口、mailbox、固件策略。物理内存区间和映射属性必须显式校验，不依靠默认假设。

每次实验保存源码提交、配置、镜像哈希、命令、boot ID/generation、双串口、阶段状态、Linux 连续性和失败原因。完整日志在服务器，Git 保存脚本、补丁和筛选后的报告；失败报告也保留。建议阈值需在空载/负载对照中校准，不能以“零网络探测丢包”替代系统正确性。
