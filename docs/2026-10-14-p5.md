# P5：完整 Windows 与外部语义解析

本阶段在同一台 QEMU/KVM 实验机器内，由持续运行的 Linux 启动完整
Windows 11 Enterprise LTSC 2024 Evaluation x64（26100.1742），并经
Linux 只读内核后端解析 Windows 页表、进程及模块。Windows 使用独占
NVMe 控制器与单个 AP；未增加内层 Windows 虚拟机或常驻分区监控器。

实现与复现命令见 [p5/README.md](../p5/README.md)，版本与构建哈希见
[sources.lock.json](../p5/sources.lock.json)。外层 KVM 提供实验硬件，
这些结果不能替代裸机验证或证明相对 KVM 的性能收益。

## 本阶段实现

| 部分 | 实现与实际边界 |
| --- | --- |
| 完整 Windows 系统盘 | 独占 PCI 子树与 64 GiB NVMe；从普通 OVMF 安装后的冷基线派生每轮独立克隆 |
| UEFI 设备访问 | 直接 ECAM、限定 BAR、分区内 identity DMA，提供 stock NvmExpressDxe 实际所需的 PCI I/O 服务；其他服务明确返回不支持 |
| 平台描述 | 新增 6 GiB 高端 RAM、MCFG、PCI 根桥 `_CRS`，与实际桥窗口匹配；Linux 早期 pci-stub 接管端点，移交前解绑根端口驱动 |
| 外部读取 | `/dev/lwobserve` ABI 2，四段允许 RAM、只读、范围和 generation 检查 |
| 独立发现 | 扫描驻留内核 PE/System 候选，关联 CR3、内核全局指针、PDB GUID/age；不接收 Windows 辅助地址 |
| 语义解析 | 4 KiB/2 MiB/1 GiB 页表、进程链表、内核模块和选定原生 x64 进程的 PEB/Ldr 模块 |
| 一致性 | 分段读与页表项复查、链表双向链接和遍历后复查、进程身份由 generation/PID/CreateTime/EPROCESS 标识 |
| 真值与生命周期 | Windows 测试进程创建/退出子进程、装卸 DLL、执行 NVMe 文件写入/刷新/读回；已知真值页在 90 秒后撤销 |

Linux 使用 CPU 0–3，Windows 使用 APIC 4，5–7 保持停驻。RAM 分区为
1536 MiB 主区、15 MiB 低端区、128 KiB 实模式区及 10–16 GiB 地址区间。
PCI 根桥预取窗口 `0x383000000000..0x3837ffffffff` 是 MMIO 地址范围，
不计为 Windows RAM。继续沿用 P3 的 IOAPIC/HPET、双串口和 IPI 协调。

## 验收方法

正式轮次为 `full03`、`full04`。每轮冷启动使用同一 Windows 基线、同一
Linux 内核和同一分区固件；记录新的 Linux boot ID 和分区 generation。
旧 generation 的读取请求必须返回 `ESTALE`。

每轮同时执行 Linux 持久 TCP 心跳、ping 和文件写入/fsync/读回。第一阶段
Linux 自行定位内核与对象，用 Windows 已知页核对 PID、CreateTime、内核
基址、子进程和 DLL。辅助页撤销后启动新的 Linux 观察进程，重新完成定位；
新进程不读取辅助页，也不继承上一进程的地址或页表缓存。

之后停止该轮实验 VM，从冷磁盘克隆转换只读 RAW，校验 GPT，通过新建
只读 loop 设备和 `ntfscat` 提取 Windows 真值日志。不在线挂载 Windows
文件系统，不修复原盘，不把宿主机 QMP 读取算作外部观察验收。

外部采样时间是遍历完成时间，Windows 日志时间又位于另一系统时钟下。
最初只比相邻两条日志时，`full03` 有 3 个不匹配，均紧邻进程/DLL 转换。
最终附加核对采用前后两秒稳定窗口，并要求日志间隔不超过两秒；排除的
转换窗口不算匹配。该方法只核对稳定时段，不能证明跨对象原子快照。
正式在线检查要求至少 10 个真值匹配、30 个独立样本；附加离线核对要求
至少 20 个稳定样本、零稳定窗口不匹配，并覆盖进程和模块生命周期。

逐轮数值与 boot ID/generation 保存在 [验收数据](p5-validation.json)。

## 调试中实际发现并修复的问题

1. **高端 DMA 被错误拒绝。** NVMe DXE 开启 dual-address-cycle 后仍可能
   使用普通 Map 枚举；原先按枚举一律拒绝 4 GiB 以上地址，导致 Identify
   失败。修复为同时检查已启用的属性，随后 WinPE NVMe 冒烟通过。
2. **固件变体复用了旧对象文件。** 覆盖层复制保留源文件 mtime，RAM 冒烟
   的较新目标文件曾被 NVMe 构建误用，`full01` 实际启动了 WinPE。固定
   Windows profile 拒绝它，没有算作成功。构建脚本现在先执行平台 cleanall。
3. **根端口资源描述不完整。** `full02` 加载了完整内核和 stornvme，但根
   端口出现资源冲突，未枚举 NVMe 子设备，最终 `0x7B`。AP 失败停驻后
   的 QMP 诊断显示设备 problem 0x0c、status `c0000018`。补齐根桥 32 GiB
   预取窗口后，`full03`、`full04` 使用的固件进入完整桌面和测试程序。

失败轮次完整日志保留在服务器 `artifacts/p5/`；`full02` 的 Linux 连续性
检查仍通过，但 Windows 启动失败，因此不算共存成功。固定固件哈希为
`9a80aca3a24aaa8c9257b1ecc8c0911170713fcc3517d29efd42a482fff5cc19`。

另外，宿主机在 2026-10-13 17:51:53 UTC 发生一次 node 5 内存策略约束
下的 OOM，日志记录业务 Python 进程和开发 VM 被杀。没有对业务进程执行
停止或重启操作；这是会影响实验的宿主机事件，不能归为 Windows 分区故障。
开发 VM 恢复后仅将其 NUMA 策略改为 preferred node 6。日志单独保存在
`artifacts/p5/host-numa-oom.txt`。

## 证据位置与限制

服务器根目录 `/data/linux-window-lab/` 下：

- `artifacts/p5/full03/`、`full04/`：Linux 连续性、UEFI 日志、独立观察、
  在线真值、停机真值及验证结果。
- `artifacts/p5/p5-package-final/`：实测内核、配置、模块及最终固件。
- `state-p5-install/windows.qcow2`：普通 OVMF 安装基线，保持关闭，不能
  在有克隆依赖时写入或替换。

观察结果证明冻结版本上的选定对象可验证，不表示所有输出字段、任意进程、
文件缓存、交换页或加密数据均能正确恢复。非驻留/变化中的页面返回不可用。
冷启动验证重启的是整个实验 VM；尚未实现 Linux 不停机下的 Windows 独立
重启、崩溃恢复或资源回收。这些属于 P6；多核 Windows 和裸机仍待验证。

当前官方评估镜像界面显示许可证过期；未使用激活或时钟绕过。P6 长稳测试
需要可持续使用的镜像。此阶段约数分钟的共存观察不能等价为长时间稳定性。
