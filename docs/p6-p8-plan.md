# P6–P8 执行计划

日期：2026-10-14。P6 已进入实现与试跑；P7/P8 仍为规划。基于 P5 提交 `6cf0af1`。
当前证据与未完成项见 [P6 进度](2026-10-14-p6-progress.md)。

## 起点与阶段划分

P5 已证明固定 QEMU 平台上，单 AP 完整 Windows 使用独占 NVMe，与 Linux
共存约 404 秒；两次冷启动均通过。58 个在线真值样本匹配，122 个独立样本中
43 个进入稳定真值窗口、79 个因转换或时间窗口被排除。辅助页撤销后的独立
扫描约 7.2–7.7 秒。详见 [P5 报告](2026-10-14-p5.md)。

下一轮将“持续运行”“独立恢复”“硬件迁移”“观察质量”“性能收益”分别验收。

| 阶段 | 回答的问题 | 主要交付 |
| --- | --- | --- |
| P6 | 多核、长时间和故障下能否维持已验证的能力？ | 多 AP 启动、压力/故障工具、观察质量改进、生命周期状态机 |
| P7 | 能否在指定真实机器上重现？ | 平台探测与清单、实机适配、裸机测试及恢复手册 |
| P8 | 能否成为可使用、可维护且价值可测的观察系统？ | 只读 API/CLI、版本支持、观察优化、对照实验与复现发布 |

主线：P6 稳定共存 → P7 固定硬件迁移 → P8 最终评估。
P8 的 API、第二版本 profile 和普通 KVM 功能基线可在 P6 后先开展。
Windows 独立恢复具有单独状态，未实现时不能宣称整个生命周期已完成。

## P6：VM 内多核、长稳与生命周期

### P6.0 固定环境与实验预算

- 获取可持续使用的 Windows 镜像。P5 评估镜像显示许可证过期，不以修改
  时钟或激活绕过支撑长稳；若更换 build，重新生成 PDB profile 并跑 P5 回归。
- 记录当前 VM、backing chain、CPU/NUMA 配置、节点内存和磁盘余量。处理
  P5 出现过的宿主机局部内存压力，设定并发 VM 数量及每节点余量门限。
  压力负载只运行在实验 VM；宿主机资源不足时停止本轮并归类为环境失败。
- 将 Windows 安装基线保持关闭，正式运行使用独立克隆；保存同 build 的
  普通 KVM 对照环境。确认控制台、日志轮转和停止实验的方法。
- 冻结构建 manifest、实验矩阵和判定规则；试跑与正式数据分开。允许试跑
  校准阈值，正式失败后调整规则必须开启新版本试验并保留旧结果。

出口：镜像/profile 匹配、单核 P5 回归通过、资源预算与恢复点齐全。

### P6.1 Windows 多核启动

1. 为 APIC 4–7 建立显式 CPU 归属、状态和栈/启动区域；Linux 保留 0–3。
   ACPI MADT/SRAT、引导入口和可用内存由同一清单生成。
2. 实现 Windows 启动 CPU 对其他分区 AP 的初始化路径，观察 INIT/SIPI、
   IPI、TLB shootdown 与每 CPU 定时器。核查 Windows 发起的广播是否影响
   Linux，不能以 P2 修复了 Linux 的广播问题推定反向路径也已安全。
3. 验证新 AP 的实际执行和调度进展，使用逐 CPU 测试线程与负载证据；
   ACPI 列出多个处理器或界面显示数量不单独构成通过。

出口目标：1/2/4 Windows CPU 配置各 3 次冷启动与 30 分钟联合负载；固定
4 CPU 配置累计 10 次冷启动。Linux boot ID 在每轮运行中不变、I/O 校验
无错误；Windows 每个分配 CPU 都有实际负载进展。两侧越权使用 CPU 或
广播破坏另一侧属于失败，保留最小复现。

### P6.2 观察质量与真值改进

- 把内核发现、对象遍历、页表翻译和读取分别计时、计字节、计重试，避免
  将启动时扫描成本混入稳态采样成本。
- 每个样本记录 Linux 单调时钟的读取起止时间。验证器使用独立真值记录的
  事件序号/时间区间及校准误差，替代仅用遍历结束时间对齐两个系统时钟。
  真值或同步信息只供验证器使用，不传递定位地址给独立观察器。
- 保留“从未开启辅助页”的正式模式；测试应用只记录真值，Linux 新进程
  必须独立发现内核及选定对象。另保留合作真值模式用于定位错误。
- 扩展 PID/地址复用、进程频繁退出、DLL 频繁装卸、分页压力、未知 profile、
  页表/链表变化等测试。稳定快照与变化窗口分开报告。
- 不支持的页面/版本明确返回 unavailable/unsupported；过期结果携带状态，
  不沿用旧对象内容冒充新采样。

出口目标：至少 1,000 个经过独立真值核对的稳定样本，至少 100 次进程生命周期
与 100 次 DLL 装卸；稳定样本误解析为 0。正式报告必须包含全部请求、有效
输出、已核对、排除、不可用和错误的数量，以及发现/撤销延迟分布。
在预先定义的稳定驻留测试负载上，真值核对覆盖目标 ≥80% 的采样请求；
达不到时继续改进或明确标为未达标，不仅发布正确率。

### P6.3 长时间联合负载

先 2 小时，再进行 24 小时固定配置试验。负载包含 Windows CPU/内存压力、
独占 NVMe 写入/flush/读回、进程/DLL 生命周期，以及 Linux 网络与文件 I/O。
分别运行观察关闭和开启的检查，确保观察器本身的影响可辨认。

出口目标：双系统持续进展、无非预期复位、数据校验无错误、无新增内核异常。
外部读取身份/generation 不混淆。持续记录工作负载速率、内存、最大心跳间隙
与 tail latency；只证明 ping 可达不够。宿主机调度/内存干扰单独归因，受影响
轮次保留但不能顶替完整 24 小时通过记录。

### P6.4 故障与分区恢复

先观测行为，再实现状态机：

`running → stop-requested → quiescing → stopped → reinitializing → running`

任一静止条件无法确认进入 `failed-retained`：保留 CPU/RAM/设备归属，禁止
重用相关内存。每步有超时、错误码、generation 和证据；超时不算已经停机。

| 场景 | 首先验证什么 | 恢复目标 |
| --- | --- | --- |
| 测试进程退出/观察器退出 | 系统仍运行，旧对象或读句柄不会误用 | 无系统重启的重新发现 |
| Windows 受控 bugcheck | Linux 连续性、AP/设备状态及最后日志 | 独立诊断，确认可否静止分区 |
| Windows shutdown/reboot | EFI、ACPI、芯片组及设备路径的实际影响 | Linux 不停机的停止/重建 |
| NVMe 超时/复位 | 中断、队列、DMA、控制器复位影响范围 | 只恢复所属设备并重建启动状态 |
| 观察期间重建分区 | 读操作与撤销同步、旧 fd/profile/cache 失效 | 旧请求拒绝，新 generation 可重新定位 |

重建前必须确认所有 Windows CPU 停止写入、设备 DMA/中断已静止，再重新
准备固件与内存。永久预留分区内存是第一版选择，返还 Linux 分配器留待后续。
暂停 CPU 不等于设备停止 DMA，也不构成完整快照。

出口目标：每类受控故障至少 5 次；Windows 独立重启连续 10 次，Linux boot ID
不变、网络/存储负载继续、Windows boot 标识及分区 generation 更新，旧句柄
拒绝。关机、崩溃后重建分别给结果。若需 Windows 合作驱动或最小虚拟化才能
完成，明确依赖并保留路线名称；不将其混入无合作/无监控层的结果。

阶段状态分为“稳定共存通过”和“独立恢复通过”。后者未达标时，P6 整体仍
注明未完成；P7 可依据前者先迁移，并继承生命周期限制。

## P7：固定硬件上的裸机迁移

### P7.0 硬件入口条件

需要专用测试机器或已明确的整机测试窗口，具备远程串口/BMC 或等效恢复方式。
当前业务服务器只用于 VM 的既有范围不改变。规划和只读硬件清点可先进行，
实际裸机改造须落实专用范围后执行。

建立 `platforms/<machine>/`：CPU/SMT/APIC/NUMA、物理地址宽度、RAM/e820、
ACPI/固件版本、PCI 根桥与桥窗口、设备复位域、IOMMU/中断重映射、启动盘和
控制台。首轮选择 Linux 和 Windows 各自独占控制器，按物理核划分 SMT 同胞。
设备 DMA、固件/SMM、时钟、电源和复位是重点待测项，不假定可按 QEMU 复制。

### P7.1 从固定地址原型转为平台适配

将 PCI BDF、ECAM/BAR/桥窗口、RAM 段、APIC ID、控制台等固定 QEMU 常量
移入经验证的平台清单。增加容量/重叠/缓存属性/设备所有权检查，启动前对照
真实硬件；不匹配时停止。保留 QEMU profile 作回归，先覆盖一台物理机。

不得把一方不再调度/驱动某资源当成另一方可立即接管的全部依据。分别确认
CPU 状态、设备驱动卸载、MSI/MSI-X/IOAPIC 状态、PCI 配置和固件运行时归属。
IOMMU 等机制可为设备兼容与稳定性采用，但不是本项目的读取保密验收目标。

### P7.2 实机逐级推进

| 顺序 | 检查 | 继续条件 |
| --- | --- | --- |
| A | Linux + 单 AP 最小 payload | 握手、异常路径和 Linux I/O 正常 |
| B | 分区 UEFI 自检 | 分配/加载/退出及平台描述一致 |
| C | WinPE | 用户态执行、Linux 持续运行 |
| D | 独占设备上的完整 Windows | 存储驱动、用户态与读回校验通过 |
| E | 多核与观察 | 1→2→4 核递进，选定对象真值通过 |
| F | 稳定性与生命周期 | 重跑 P6 已实现能力，并记录硬件差异 |

出口目标：固定硬件与固件版本，完整配置 10 次冷启动，2 小时与 24 小时联合
负载通过；无 Linux 内存/存储覆盖证据；外部观察的身份、版本及稳定样本校验
通过。Windows 分区恢复仅在本硬件实测后列为支持能力。保留救援启动项、冷
备份和失败恢复步骤，不将一种硬件成功写成普遍兼容。

## P8：观察系统完善与最终评估

### P8.1 可使用的只读观察接口

首个接口范围：列举进程、列举内核模块、列举目标原生 x64 进程模块、翻译
指定 VA、读取指定进程的有界 VA 区间。使用 `(generation, PID, CreateTime,
EPROCESS)` 对象句柄，防止 PID 复用；输出 profile 身份、起止时间、状态和
不可用原因。Linux 本地工具/API 先行，暂不建设远程控制平面或网页产品。

演示任务固定为观察一个受控应用的进程和 DLL 变化，读取其带序号的目标
缓冲区，应用退出后拒绝旧句柄。明确外部读取不经过 Windows 对象访问接口；
可选用无读取权限的普通 Windows 账户做对照，实际目标数据仍为自有测试数据。

### P8.2 版本与读取成本

支持至少两个固定 Windows build：各自冻结介质、PE/PDB 身份、profile、
引导和观察结果。未知/错误 profile 必须拒绝解析。第二 build 的通过条件
包含实际共存启动，不能只生成偏移文件。

在 P6 数据基础上优先优化重复扫描、过碎 ioctl、批量页读取和重复对象遍历。
任何缓存均明确 generation/对象身份与失效条件，并用进程复用、页表变化和
分区重启回归。分别报告冷发现、重发现、稳态采样、页表翻译和内容读取成本。
首个交付仍不包含任意分页文件恢复、全文件系统解释或任意跨对象原子快照。

### P8.3 公平对照与结论

| 路线 | 作用 |
| --- | --- |
| Windows 裸机独占 | 硬件与 Windows 工作负载基准，记录 CPU/内存限制及差异 |
| Linux + 优化 KVM Windows | 专用 CPU、匹配 NUMA/内存、可用时同设备直通；同时保留相同 Linux 负载 |
| Linux–Windows 裸机分区共存 | 本项目主结果，同资源与工作负载；观察关闭/开启/多种频率 |
| 最小虚拟化静态分区（若实际实现） | 独立路线，单独报告常驻职责及恢复/成本差异 |

匹配 Windows build、CPU/SMT、可用 RAM、设备、频率/电源策略、负载和运行
时段，记录无法匹配的项目。普通 KVM 使用匹配的解析工作与采样频率做读取
对照，并说明后端差异。P5 外层 QEMU 内共存只作功能回归。

测量 Windows/Linux 吞吐、p50/p95/p99 延迟与抖动、观察开启造成的工作负载
变化、观察 CPU/内存/物理读取量、有效语义样本速率、真值覆盖率和检测延迟，
以及启动/恢复时间。P4 重复读取页的字节吞吐不作为新数据速率。

先试跑确认预热与稳态区间，再冻结正式配置；主要性能点至少 5 次独立运行，
报告各次值、区间和失败轮次，尾延迟附样本量与采样方法。长稳另外报告。
性能改进没有预设百分比：正确性通过且比较完整，负收益也作为有效结论保留。

### P8.4 交付与发布

从干净环境按文档完成一次独立重建/部署/验证。保存构建与平台 manifest、
测试命令、原始证据索引和校验和、结果汇总、分析脚本、支持矩阵与恢复手册。
不分发 Windows 系统镜像、凭据或有许可证限制的构建输入。

出口：两 build 回归通过、未知版本拒绝、选定应用演示可复现、公平对照与
数据完整。发布说明明确平台、CPU 数量、设备、版本、恢复能力和观测限制。

## 优先级与检查点

1. **立即进入 P6.0**：先解决镜像、资源预算、基线与试验判定规则。
2. **P6.1/P6.2**：多核和观测质量可作为独立工作包推进；通过后运行 P6.3。
3. **P6.4**：在独立克隆上做故障/恢复，避免污染长稳证据；静止机制是关键
   研究检查点，不能承诺仅改 ResetSystem 即可完成。
4. **P7**：硬件清点可以提前；实际迁移依赖专用范围和 P6 稳定共存通过。
5. **P8**：接口和对照准备可提前，最终比较等待实机结果及配置冻结。

按工作包给出进度与证据，不对尚未识别的平台问题承诺固定总工期。每个包
包含代码提交、测试配置、原始日志、通过/失败条件和下一步；只有对应验收
实际通过才更新完成状态。P6 按后续用户授权推进；P7 裸机试验仍待专用测试范围落实。
